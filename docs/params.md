# 参数说明

`start-llama.sh` 里每个参数为什么这么设。只在一台机器上测过（见 README「实测环境」），换了显卡、内存或 llama.cpp 版本，数字会变。

## 放显卡还是放内存

| 参数 | 作用 | 为什么 |
|---|---|---|
| `--fit on` | 按显存自动分配：放不下的部分挪到内存 | 这一版默认就是 `on`，写出来是为了看得清楚。不用手算 `--n-cpu-moe`。用 llama.cpp 自带的 `llama-fit-params` 看过分配结果：上下文 32k 时，第 20–40 层的专家权重（外加第 19 层的 down）放内存，其余全在显卡上 |
| `--device CUDA0` | 只用这一块显卡 | 明确指定独显；多显卡的机器按自己的改 |
| `-c 32768` | 上下文 32k | 给 Agent 用，16k 不够：工具说明 + 几轮工具结果很快就满，反复压缩会拖慢很多（见 README「实测」） |
| `-ctk q8_0 -ctv q8_0` | KV 缓存用 8 位 | 省显存，好让更多层留在显卡上 |
| `-np 1` | 只开一个槽位 | 一个人用；多开几个槽位，KV 缓存也要多占几份 |
| `--load-mode none` | 不用内存映射加载模型 | **这是 32 GB 机器上最关键的一个参数**，见下面 |
| `-ub 2048 -b 2048` | 一次送进显卡算的 token 数从默认 512 调到 2048 | **读提示快将近一倍**（1,474 → 2,844 token/秒），生成速度不变。原因：放在内存里的专家，读长提示时要按层整块拷到显卡上算，每个批次拷一遍；批次越大，拷的次数越少。4096 只再快约 10%，生成反而慢一点、内存多 1.4 GB，不划算。见 `docs/benchmarks.md` |
| `--cache-ram 1024` | 提示缓存在内存里最多占 1 GB（默认 8 GB） | 只有一个槽位时，旁路请求（比如框架给会话起标题）会把主对话挤出去，主对话的状态存在这块缓存里、回来再恢复。实测 1 GB 和 8 GB 一样能恢复（旁路请求之后只重读 34 个 token），进程内存少约 0.5 GB；设成 0 就要整段重读（4,103 token、1.8 秒） |
| `--sleep-idle-seconds 1800`（`SLEEP_IDLE_SECONDS`） | 空闲 30 分钟后把模型从内存和显存卸掉，进程不退出，下一个请求进来自动载回 | 32 GB 机器上模型开着不用时最占地方。实测睡下后进程内存 8.76 → 0.58 GB、显存 10,654 → 609 MiB（剩下的是别的程序），系统可用内存 8.1 → 16.3 GB；醒来的第一个请求等 8.6 秒，回答正常。睡着时查 `/props` 不会叫醒它（`/health` 没测）。代价：醒来后前缀缓存没了，第一轮要整段重读 |
| `--moe-cache-mib`（可选，`MOE_CACHE_MIB=2048`） | 在显卡上留一块缓存，放最近用过的「内存里的专家」 | 生成快约 30%（57 → 75 token/秒），但缓存占了显存，`--fit` 只好多挪一些专家到内存：读提示慢约 25%、每步读工具结果多 0.2 秒、进程内存多约 2 GB。按 Agent 一步「读 200、写 200 token」算，每步快约 16%。内存够用（模型开着时系统还剩 4 GB 以上）再开 |

### 为什么要 `--load-mode none`

默认（`auto`）会把模型文件映射进内存。实测：

| 加载方式 | 进程常驻内存 | 显存 | 测试期间系统剩余内存最低 | 生成速度 |
|---|---|---|---|---|
| 默认（映射） | 最多 1.6 GB，但整个模型文件（16.5 GB）的页面都挂在进程上 | 9.8 GB | **0.34 GB** | 约 51 token/秒 |
| `--load-mode none` | 最多 10.3 GB（放内存的专家 + 缓存） | 9.9 GB | 5.1 GB | 约 62 token/秒 |

映射时，放到显卡上的那部分权重在文件缓存里也留着一份，32 GB 内存差点被吃光。llama.cpp 自己也会提示「专家放 CPU 时，用映射会更慢」。不映射之后，只有放内存的那部分专家常驻，速度也更快。

### 看占多少内存，别看「私有字节」

在 Windows 上，刚加载完、还没收到请求时，llama-server 的「私有字节 / 提交大小」就有约 11 GB，其中约 9.5 GB 是 152 块 64 MB 的分配，大小和显存用量几乎一样，看起来是显卡驱动给显存记的账（只算提交量，没占内存条）。要看真实占用，看性能计数器 `\Process(llama-server)\Working Set - Private`，再加上显存。

## 采样（防复读）

| 参数 | 值 |
|---|---|
| `--temp` | 0.7 |
| `--top-p` | 0.8 |
| `--top-k` | 20 |
| `--min-p` | 0 |
| `--presence-penalty` | 1.5 |

这五个都是 Qwen3.6 非思考模式的官方推荐值。

**为什么不用 DRY 了（2026-10-23 改）**：最早用 llama.cpp 的默认采样（温度 0.8、top-k 40、top-p 0.95、不防复读）时，Agent 填工具参数两次陷进复读，一个短名字被写成同一串字反复重复、写到 4096 的输出上限。当时同时换了采样参数、加了 DRY 防复读（`--dry-multiplier 0.8`），之后再没复读过。

但 DRY 会伤到 Agent 最常做的一件事：**把一条长路径原样再写一遍**。DRY 惩罚「刚出现过的一整段」，路径里的 `\` `/` `-` 又不是它的断点，路径越长、刚写过的次数越多，罚得越重。实测：
- 工作目录写在系统提示里、让模型在一条回复里用完整路径读 6 个文件（Agent 框架的真实情况），跑 12 次：DRY 0.8 只有 26/72 条路径一字不差，错成 `deepsee-harness`、`deeepsee-harness`、`radme.md`；presence 1.5 和不防复读都是 72/72
- 在 DSH 里跑同一个「读两个文件、写一个文件」的任务：DRY 0.8 三次都抄错路径（错 3、11、1 次，多花好几步）；不防复读三次、presence 1.5 两次都没错，都是 3 步完成
- 换成 presence 1.5 后，DSH 里的多文件压力任务（建 5 个文件夹、写 6 个文件）也没出现复读

presence penalty 对已经出现过的 token 只罚一次，不会越罚越重。它也只看最近 64 个 token（`--repeat-last-n` 默认值）。

很多 Agent 客户端不传采样参数，这时就用这里的服务端默认值，所以写在启动脚本里。

## 关掉思考

`--jinja --reasoning-format deepseek --chat-template-kwargs '{"enable_thinking":false}'`

- `--jinja`：按模型自带的模板生成工具调用，Agent 要用
- 关思考：在服务端关，客户端不用管。之前在同一台机器上跑稠密的 27B 模型时，开着思考常常一轮答不完；换成这个 MoE 模型后一直关着用，没再试过开
- 这一版的 llama.cpp 已经有新写法 `--reasoning off`，`--chat-template-kwargs` 的写法标成了过时，但现在还能用。脚本里用的是实测过的旧写法

## 安全

llama-server 的默认设置是给本机试玩用的：不要密钥、跨域允许任何来源（`--cors-origins` 默认 `*`）、`/slots` 能看到正在处理的对话。意思是你浏览器里开着的任何网页都能在后台调你的模型、读你的对话。所以：

| 参数 | 作用 |
|---|---|
| `--host 127.0.0.1` | 只听本机，局域网连不进来 |
| `--api-key-file` | 要密钥；密钥放在文件里，不写进命令行（命令行别的进程看得到） |
| `--cors-origins localhost` | 跨域只认本机来源 |
| `--no-slots` | 关掉 `/slots` |

## 别名

`--alias qwen3.6-35b-a3b`：接口里的模型名。客户端（Agent）配置里的模型 id 要和它一样。
