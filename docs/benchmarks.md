# 优化实测（2026-10-23）

一台机器上把网上找到的优化办法一项项测过，只留下实测有用的。测法和每个字段的意思见 `bench/README.md`，原始结果在 `bench/runs/`。

**环境**：ROG Strix G16（Ryzen 9 9955HX3D、RTX 5070 Ti Laptop 12 GB、32 GB DDR5 两条不同牌子跑在 4800）、Windows 11；模型 unsloth `Qwen3.6-35B-A3B-UD-IQ4_XS`。每项 3 次取中位数，同一配置隔一段时间再测会差 ±5% 左右。

## 结论

| | 优化前（b11259，默认批次） | **默认**（b11836 + `-ub 2048` + `--cache-ram 1024`） | **快速**（再加 `MOE_CACHE_MIB=2048`） |
|---|---|---|---|
| 读长提示（约 7.5K token） | 1,235 token/秒 | **2,780**（×2.25） | 2,028（×1.64） |
| 生成（长上下文后） | 48.7 | 57.3 | **74.6**（×1.53） |
| 生成（真实任务） | 50.9 | 58.4 | **75.1**（×1.48） |
| 读一次约 200 token 的工具结果 | — | **332 毫秒** | 569 毫秒 |
| Agent 第一轮（读 4,044 token） | 2.9 秒¹ | **1.6 秒** | 2.3 秒 |
| 进程内存 | 9.9 GB | 10.1 GB | 12.0 GB |

¹ 这一格是 b11836 + 默认批次测的（b11259 没跑多轮 Agent 测试）。

- **默认**：读得快，内存和优化前差不多。32 GB 机器上同时还开着别的软件时用这个
- **快速**：写得快，读得慢一点，内存多约 2 GB。按 Agent 一步「读 200、写 200 token」算，每步比默认快约 16%

## 每一项

### 有用，已采用

| 改动 | 结果 |
|---|---|
| llama.cpp b11259 → b11836 | 读提示 1,235 → 1,474（+19%），生成持平。新版 CUDA 上有 Gated DeltaNet 的分块内核（这个模型 40 层里 30 层是 DeltaNet），还修了锁页内存、提示缓存恢复等问题 |
| `-ub 2048 -b 2048`（默认 512） | 读提示 1,474 → 2,844（+93%），生成不变，内存 +0.3 GB。放在内存里的专家，读长提示时要按批整块拷到显卡；批次越大拷得越少 |
| `--cache-ram 1024`（默认 8192） | 和 8 GB 一样能在旁路请求后恢复主对话（只重读 34 token），进程内存少约 0.5 GB。设成 0 不行：旁路请求后整段重读 4,103 token（1.8 秒） |
| `--moe-cache-mib 2048`（可选） | 显卡上缓存最近用过的「内存里的专家」。生成 +30% 左右；代价见上表。1 GB 时生成 68、读提示 2,198；1.5 GB 时 68 / 2,071；2 GB 时 74 / 1,916；3 GB 时（不配大批次）系统可用内存只剩 1.6 GB，太险 |
| `--sleep-idle-seconds`（默认 1800） | 空闲后自动卸载模型：进程内存 8.76 → 0.58 GB，显存 10,654 → 609 MiB，系统可用内存 8.1 → 16.3 GB；下个请求自动载回，第一次回答等 8.6 秒，答案正确（测试时设的 30 秒） |

### 绑核（只对这块 CPU 有效，可选）

9955HX3D 有两块 CCD：逻辑处理器 0–15 是带 3D V-cache 的那块，16–31 是另一块；同一个核的两个超线程编号相邻（这些是在本机上读 CPU 拓扑得到的）。生成时放在内存里的那一半专家由 CPU 算，卡在内存带宽上。

| 线程设置（默认配置下） | 生成（长上下文后） | 生成（真实任务） |
|---|---|---|
| 默认（16 线程，不绑核） | 56.6 | 58.3 |
| 8 线程，16 线程（都不绑核） | 55.4 / 55.3 | 56.7 / 57.4 |
| **8 线程绑另一块 CCD，每核一个**（`-t 8 -C 55550000 --cpu-strict 1`） | **59.3**（两次测都是 59.3） | **61.0** |
| 同上，不加 `--cpu-strict` | 59.1 | 61.0 |
| 6 线程绑另一块 CCD | 55.0 | 56.6 |
| 8 线程绑 V-cache 那块（`-C 5555`） | 50.6 | 51.6 |
| 16 线程绑 V-cache 那块（含超线程，`-C ffff`） | 46.4 | 46.4 |
| 16 线程绑全部 16 核，每核一个（`-C 55555555`） | 51.9 | 51.7 |

- 默认配置下，绑另一块 CCD 快约 5%；绑 V-cache 那块、或者横跨两块绑满，都更慢。原因没查实，可能是 V-cache 那块频率更低，而这里用不上大缓存
- 快速配置（专家缓存 2 GB）下再绑核，75.8 对 74.6，在波动范围里
- 掩码只适用于这种编号方式的 CPU。别的机器先查清楚哪些逻辑处理器属于哪块 CCD 再试，要用就加在启动命令后面：`bash start-llama.sh -t 8 -C 55550000 --cpu-strict 1`

## 第二轮（2026-10-23 下午）：Agent 这一侧

上午测的都是推理本身。下午换到「接上 DSH 以后」：用真的 DSH 跑任务、看 llama-server 日志里每一步重读了多少，再对照 DSH 源码。这一轮测试时 Ollama 也开着、占了约 2 GB 显存，所以绝对速度比上午低，只在同一时段内比较。

### 防复读：DRY 换成 presence penalty（已改）

在 DSH 里跑「读 notes.txt 和 todo.txt，整理后写进 plan.md」，第一次就看到模型把 `deepseek-harness` 写成 `deepseek-hardware`，后面的重试路径被截断成 `deepseek-`、`deep`。工作目录这串长路径已经在系统提示里出现过，DRY 正好专罚这种「刚出现过的一长段」。

| 防复读设置 | DSH 里的读写任务 | 测速脚本：工作目录在系统提示里，6 个文件 × 12 次 |
|---|---|---|
| DRY 0.8（原来的） | 3 次都抄错路径（错 3 次、11 次、1 次），4 到十几步、26 秒以上 | **26 / 72** |
| 不防复读 | 3 次都没错，3 步、13–18 秒 | 72 / 72 |
| **presence 1.5**（官方推荐，现在用的） | 2 次都没错，3 步、14–18 秒；多文件压力任务（5 个文件夹、6 个文件）也正常 | **72 / 72** |

上午那个测法（中文长路径写在用户消息里）三种设置都是 72/72，所以没测出来。测速脚本里两种测法都保留了（`--copy` 和 `--copy-cwd`）。

**presence 1.5 会不会罚路径里重复的字？** presence penalty 也看提示末尾 64 个 token，而翻唱项目的路径里歌名常常出现两次（`E:\workspace\公主\r02\公主_扒谱_定稿（10-07_23.40存）.svp`）。加了一种测法（`--copy-cn`：中文工作目录、文件名里重复歌名），presence 0 / 0.5 / 1.5 各 12 次：英文目录和中文目录全部 72/72，工具调用漏进正文（llama.cpp #30118 报过的问题）0 次。所以保留官方推荐的 1.5。

### DSH 每一步只重读新加的部分

一次两轮 14 个请求的 DSH 会话：除了第一轮读 4,822 token（2.95 秒），每一步只重读 20–453 token。批次改成 2048 以后，「提示结尾往前一个批次」的检查点离末尾更远了，如果框架每步都改末尾的内容，就会多重读；DSH 是纯追加，所以没有这个问题。模型一共用了 36.9 秒：生成 29.2 秒，读提示 7.7 秒。对 DSH 来说，生成速度比读提示速度更要紧。

### DSH 的输出上限（已改补丁）

读 DSH 源码发现，单次工具输出默认最多能塞 12,500 token 进上下文（`spill-policy`），读文件默认一次 50 KB。补丁里改成 4,000 token / 16 KB，网页抓取 200,000 → 12,000 字，说明文件 65,536 → 16,384 字节。改完用 `--dump-config` 核过，再在 DSH 里让模型用命令行打印一个 18 万字节的日志（不截的话约 4.5 万 token，窗口装不下）：那一步只重读了 5,749 token，上下文用到 33%，模型照样答对了第一行和最后一行（输出落盘后上下文里留了头尾）。之前文档里说「压缩组的 pruner 限制单次输出」是错的，它只在压缩时运行。

### 端到端：默认 vs 快速

`bench/agent_task.py` 照 DSH 的方式跑一个多步任务（读 data.csv，建 5 个文件夹写 6 个文件），两种配置交替各 3 次：

| | 总耗时 | 读提示 | 生成 | 生成 token 数 |
|---|---|---|---|---|
| 默认 | 18.8 / 16.9 / 19.0 秒 | 3.4–3.6 秒 | 13.4–15.4 秒（约 54 token/秒） | 720–815 |
| 快速 | 15.6 / 15.8 / 14.8 秒 | 4.9–5.1 秒 | 9.8–10.8 秒（约 63 token/秒） | 601–658 |

快速配置看起来快 15% 左右，但它这几次恰好写得少。按同样写 750 token 折算：默认约 17.4 秒，快速约 16.9 秒，只快约 3%——读提示慢掉的部分把生成省下的吃掉了大半。会话越长、每步新读的越少，快速配置越划算；短任务差不多。所以默认不开专家缓存。

### llama.cpp 升到 b11840

b11840 比 b11836 只多了一个有用的修复：Windows 上 llama-server 连续运行约 10.5 天会因计时溢出崩溃（#30969）。之后的下一个提交把 CUDA 构建弄坏过（#30804，已由 #31053 修好，还没出新版本）。

## 第三轮（2026-10-23 晚上）：别的引擎和量化

### PolyStrata：这台机器内存不够

[PolyStrata](https://github.com/VecSzn/PolyStrata)（Strata 的衍生项目，10 月新出，421 星）为 Qwen3.6 写了自己的引擎：按使用频率把专家缓存在显存里，没命中的在 CPU 上算，还会跳过排名靠后的低概率专家（`--tail-skip 6`，近似计算）。作者在 8 GB 显卡 + 32 GB 内存的笔记本上报了 82–86 token/秒（UD-Q4_K_M）。

在这台机器上装了它的发布版 v0.1.45-poly.2（现成的 Windows 引擎，不用编译）和它指定的 UD-Q4_K_M（22.7 GB）。显存放下了 10,496 个专家里的 3,799 个（6.8 GiB），剩下约 16 GB 要进内存，而这台平常开着各种程序时可用内存只有约 15 GB：两次启动都把可用内存压到 1 GB 以下，被看门狗停掉，没测出数字。它的 UD-Q3_K_M（17.1 GB，约 17 GB 内存）也许塞得下，但质量比 IQ4_XS 低一档，没测。

**注意**：PolyStrata 主分支的代码如果找不到对应的现成引擎包，安装脚本会自动用 winget 以管理员权限装 Visual Studio Build Tools 和 CUDA Toolkit（加 `--yes` 时不会问）。要装就切到它的发布版标签，先确认引擎包存在。

### 客户端量的基线（流式接口、从客户端计时）

为了和别的引擎用同一把尺子比，写了一个只当客户端的测速（读长提示的首字延迟、生成速度、抄路径、多步 Agent 任务）：

| | 读提示 | 生成（长上下文后 / 真实任务） | 多步任务 | 抄路径（英文 / 中文工作目录，各 48 条） |
|---|---|---|---|---|
| 默认 | 2,758 | 51.1 / 53.2 | 18.5 秒 | 48 / 45（有一次少发了一个调用，没有写错的路径） |
| 快速 | 1,803 | 66.1 / 63.0 | 18.0 秒 | 48 / 48 |

### n-gram 投机解码：改写文件快 2–3 倍（可选）

Agent 改文件时，经常要把上下文里的一大段原样再写一遍。llama.cpp 的 `--spec-type ngram-mod` 用上下文里已经出现过的片段当草稿，一次校验几十个 token，不需要额外的模型。测速脚本加了「改写文件」测试（`--rewrite`：约 1,500 token 的代码，改一个函数名、其余原样输出）：

| 测试组 | 不开 | ngram-mod | 输出 |
|---|---|---|---|
| 第十七组 | 约 50（同组其他配置） | **117.3**（门槛不调）/ 88.8（`GGML_OP_OFFLOAD_MIN_BATCH=128`） | 一字不差 |
| 第十九组（机器降频、被别的任务占着） | 30.9 | **87.7** | 一字不差 |

- 草稿接受率约 63%，每次平均接受 41 个 token
- 把专家整块传到显卡上校验的门槛（`GGML_OP_OFFLOAD_MIN_BATCH`）不用调：这台是 PCIe 5.0，传过去校验反而更快；`ngram-map-k` 是 103.2，也不如 ngram-mod
- 正确性：多轮 Agent 每一步重读的 token 数和不开时一样（追问 24、旁路请求后 34），两种抄路径都是 72/72，工具调用漏进正文 0 次，没出现过卡死（llama.cpp #23268 报过混合模型在温度 0 的工具调用里可能卡住，没碰到）
- 写新内容时基本没影响（真实任务 50.3 对约 50）；续写随机词表那一项慢了 5–15%

要用就加在启动命令后面：`bash start-llama.sh --spec-type ngram-mod`。默认不开：只在机器安静时测了一组，写新内容时可能有轻微损失。

### byteshape Q4_K_S-4.22bpw：生成略快、读提示略慢

研究时发现，我们用的 unsloth UD-IQ4_XS 里，40 层专家的 gate/up 都是 IQ3_S 格式，在 CPU 上算得慢（每 32 个权重要查 8 次表）。byteshape 的 Q4_K_S-4.22bpw（18.3 GB）专家用 K-quant，厂商测的综合精度 0.9915（UD-IQ4_XS 是 0.9946），纯 CPU 解码快约 35%。实测：

| | 读提示 | 生成（长上下文后 / 真实任务） | 改写文件 | 抄路径 | 进程内存 |
|---|---|---|---|---|---|
| UD-IQ4_XS | 2,650 | 52.2 / 53.2 | 50.2 | 72 / 72 | 9.8 GB |
| Q4_K_S-4.22bpw | 2,357（−11%） | 54.7 / 56.4（+5–6%） | 56.8 | 72 / 72 | 10.4 GB |

只快 5–6%，说明 CPU 那一半主要还是卡在内存带宽上。读提示慢了、内存多了，不换成默认。

### OpenMP 空等设置和 `--prio`：没用

`KMP_BLOCKTIME=0` 变慢（生成 37）；`KMP_BLOCKTIME=infinite`、`OMP_WAIT_POLICY=ACTIVE`、`--prio 2` 都在 49–52，和不设一样。

### 快速配置在机器忙的时候会崩

晚上这几组测试时，显卡已经连续满载几个小时、到了 85–87°C、在温控降频，另一个程序同时占着约 8 个 CPU 核，系统可用内存一度只剩 1.4 GB。这种情况下快速配置（专家缓存 2 GB）读提示从约 1,800 掉到 160–170、生成掉到 21–32，默认配置只是整体慢一些。所以内存紧、机器忙的时候别开快速配置。

### 看了没测的

- **专家剪枝版（REAP 等）**：剪枝的校准集几乎都是代码，通用文本和知识掉得比同体积的低位量化还多；没人测过中文
- **更小的量化（UD-IQ3_S 13.7 GB、UD-Q2_K_XL 12.3 GB）**：能多放专家到显卡，但质量掉一档，中文和工具调用要自己测
- **把提示缓存存到磁盘、重启后恢复**（`--slot-save-path` + `/slots/0?action=save|restore`）：b11840 已经支持混合模型的检查点，能把重启后第一轮重读系统提示的约 1.7 秒省掉；空闲卸载醒来时用不上（醒来本身要约 9 秒）
- **llama.cpp #30966**（没命中的专家在 CPU 上算）：还没合并
- **换同型号的一对内存条（4800 → 5600）**：理论带宽 +17%，估计生成快 5–10%，要自己换

## 显存爆了不报错

测 ik_llama.cpp 时手动设 26 层专家放内存，显存峰值到了 11,843 MiB（一共 12,227），结果读提示从两千多掉到 200 token/秒、生成从六七十掉到 13，服务照常回答、没有任何报错。看起来是 Windows 显卡驱动在显存不够时悄悄借用了内存（没有进一步查证）。用 `--fit on` 自动分配（本仓库的默认）不会碰到；手动设层数、或者开着别的吃显存的程序时要留意。下面「NVIDIA 控制面板」那一条可以让它直接报错。

## 要你自己动手的（可选）

这些是调研 + 本机只读检查得出的，没有实测收益：

- **让桌面走核显**：现在显示器挂在独显上，桌面、浏览器、动态壁纸等占了约 0.8 GB 显存。在 Armoury Crate 里把 GPU 模式切到「标准 / Optimus」，`--fit` 就能多放约两层专家到显卡上。打游戏时再切回来
- **NVIDIA 控制面板**：只给 `llama-server.exe` 设「CUDA - 系统内存回退策略 = 首选无系统内存回退」。不会变快，但显存不够时会直接报错，不会悄悄退到内存里变慢
- **内存条**：两条不同型号，标称 5600 实际跑 4800。换成同型号的一对，理论带宽 +17%；生成时 CPU 那一半卡在内存带宽上，估计能快 5–10%
